# 에이전트용 검수 브리프

[English](../agent-brief.md)

**QAMap 0.5.1 이상이 필요합니다.**

`qamap qa brief`는 코딩 에이전트가 바로 검수할 수 있는 한 개의 텍스트 브리프를
출력합니다. 에이전트는 읽는 분량뿐 아니라 모델 호출 횟수만큼 토큰을 씁니다.
호출할 때마다 호스트의 시스템 프롬프트와 지금까지의 대화를 다시 보내기 때문입니다.
LLM 단독으로 PR을 검수하면 보통 `git diff`, 검색, 파일 읽기에 여러 번 호출을
씁니다. 브리프는 그 근거를 LLM 호출 없이 로컬에서 한 번에 모읍니다.

```sh
qamap qa brief
```

기준 브랜치는 CI 정보, 저장소 설정, Git 이력 순서로 자동 선택합니다. PR의
기준 브랜치가 다르면 `--base <ref>`, 커밋하지 않은 변경을 포함하려면
`--include-working-tree`를 추가합니다. 기본 크기 한도는 24,000바이트이며
`--max-bytes <n>`으로 바꿀 수 있습니다(최소 4,000). 전체 보고서는 계속
`~/QAMap-reports/qa-*`(또는 `--output <directory>`)에 저장되지만, 브리프는
에이전트에게 그 파일을 읽으라고 안내하지 않습니다.

미추적 파일의 내용이 생략되면 `git diff --no-index -- /dev/null '<file>'`로
복구하도록 안내하며, 추적 중인 파일의 복구 명령과 구분합니다. 이 명령은
차이를 발견하면 종료 코드 1을 반환하며 파일을 스테이징하거나 실행하지 않습니다.
미추적 파일이 여러 개면 `<untracked-file>`을 목록의 각 경로로 바꿔 실행합니다.

## 브리프에 들어가는 내용

| 항목 | 내용 |
| --- | --- |
| 머리말 | 비교 범위, 변경 파일 수, 직접 또는 호출자를 통해 테스트 참조를 수집한 변경 선언 수(실행된 커버리지가 아님), 감지한 프로젝트와 기존 검증 명령. 다 담지 못하면 그 사실을 한 줄로 알립니다. |
| 변경 | 줄 번호가 붙은 diff. 문맥 줄과 `+` 줄은 head 기준, `-` 줄은 base 기준 번호입니다. 150줄 이하 파일은 전체를, 작은 함수는 함수 전체를, 그 외에는 앞뒤 8줄을 보여줍니다. 줄 한도를 넘는 파일은 삭제된 줄을 모두 남기고, 길게 이어진 추가 줄은 head 줄 범위로 접습니다. head 파일을 읽으면 추가된 줄은 볼 수 있지만 삭제된 줄은 볼 수 없기 때문입니다. |
| 변경 신호 | 소스 파일마다 놓치기 쉬운 동작 변화를 패턴으로 찾아 줄 번호와 함께 적습니다. 줄어든 error·warning 로그, 없어지거나 추가된 오류 처리, 새 throw나 오류 반환(던지는 이름 포함), 그 경우가 이제 계속 진행되는 삭제된 throw, 새 조기 종료, 삭제된 조건, 빠진 `await`, 없어진 트랜잭션이나 잠금, 다시 쓴 권한 조건(빠진 조건과 추가된 조건), Go·JavaScript·Python 초기화에서 빠졌지만 아직 읽히는 키, 이번 diff가 선언하고 읽지만 값을 넣지 않는 필드입니다. 결함 판정이 아니라 읽어야 할 위치입니다. 모든 파일을 다 보여줄 수 없을 때도 파일마다 머리줄과 신호는 남깁니다. |
| 안 보인 줄 | 한 선언 안의 두 hunk 사이에 보이지 않은 변경 없는 줄이 10줄 이상이면, 그 선언의 head 범위와 해당 줄 |
| 사용처 | 변경된 선언마다 그 이름을 쓰는 테스트(제목, 호출, 그 결과에서 나온 지역 변수, 그 값을 쓰는 단언), 호출하는 코드와 그 소속 선언, 그 호출 코드의 테스트. 이번 diff가 바꾼 줄의 사용처에는 `(changed)`를 붙이고, 표시가 없으면 바뀌지 않은 사용처입니다. 다른 언어의 같은 이름과 주석 줄은 넣지 않습니다. 선언이 직접 또는 바뀐 하위 함수를 통해 새로 throw하면, try 블록·`.catch`·Go 오류 검사가 없는 호출자를 먼저 놓고 호출마다 패턴으로 찾은 처리 방식을 표시합니다. |
| 호출 대상 | JavaScript와 TypeScript는 head의 변경된 줄에 있는 호출을 바인딩으로 확인해 정의 위치와 12줄 이하의 본문, 모듈 위치를 확인하지 못한 리터럴 import 경로, 또는 사용 위치가 있는 미확인 바인딩을 표시합니다. 삭제된 호출은 diff에 남습니다. 다른 언어는 기존 패턴 기반 조회를 유지합니다. 운영 코드에는 테스트 헬퍼를 정의로 제시하지 않습니다. |
| 변경된 테스트 계약 | 테스트 diff를 온전히 표시하지 못하면 수집한 테스트 제목과 선언 위치를 제한된 목록으로 남깁니다. 단언 상세를 먼저 줄이고, byte 예산으로 항목을 빼면 빠진 제목·위치의 개수를 표시합니다. 저장소의 기대값이며 실행 결과가 아닙니다. |
| 이력 | 삭제되거나 바뀐 줄을 처음 넣은 커밋과, 그 커밋이 함께 추가한 테스트(줄 번호 포함) |
| 검증할 항목 | 추론한 변경 의도별 동작 흐름(trigger, 조건, 동작, 상태, 결과)과 중요 시나리오의 모든 확인 항목(경계 사례 포함). 패턴으로 고른 휴리스틱 점검이므로, 검수자는 이 diff에 맞는 항목만 "동작 → 기대 결과"로 바꾸고 맞지 않으면 한 줄로 제외합니다. 신뢰도가 high가 아닌 의도의 중요 시나리오는 `[check]`로 표시합니다. |
| 미확인 | 실행 시점에 고르는 모듈, 모호한 re-export, 테스트 참조를 수집하지 못한 변경 선언 |
| 전부 보이지 않은 파일 | diff를 전부 보여주지 못한 모든 파일, 빠진 삭제·추가 줄 수, 그 줄을 보여주는 `git diff` 명령 |

초기화에서 빠진 키는 그 값을 읽는 코드도 최대 64자까지 함께 보여줍니다.
값이 할당되지 않은 필드는 읽는 줄과 같은 이름의 지역 변수 선언을 각각 최대
60자까지 표시합니다. 기존 파일별 신호 길이 제한과 브리프 전체 크기 제한은
그대로 적용됩니다.

JavaScript와 TypeScript에서는 같은 파일의 `async` 함수를 `await` 없이
`if`나 `while` 조건에 직접 호출하는 변경을 표시합니다. 지역 이름의 실제
바인딩을 확인하므로 같은 이름의 매개변수나 지역 변수는 구분합니다. 이미
`await`한 호출, 명시적인 비교, 외부에서 가져온 함수, 제너레이터, 재할당된
함수는 제외하며 파일마다 최대 두 건을 표시합니다. 실제 결함을 확정하거나
테스트를 실행한 결과는 아닙니다.

새 오류 경로는 같은 파일의 기존 래퍼 호출도 최대 세 단계까지 따라갑니다.
래퍼 자체가 수정되지 않았어도 그 호출자를 보여주며, 패턴으로 찾은 try 블록,
`.catch`, Go 오류 검사나 오류 버리기는 전파를 멈춥니다. JavaScript와
TypeScript는 지역 바인딩도 확인하고 다른 언어는 패턴으로 찾습니다. 모든
제어 흐름이나 파일 사이의 예외 전파를 분석하는 기능은 아닙니다.

JavaScript와 TypeScript에서는 바뀐 `setTimeout`, `setInterval`,
`addEventListener`, `.subscribe` 호출과 같은 함수 안의 정리 코드를
비교합니다. 함수가 바로 반환하는 정리 함수도 확인합니다. 등록 코드는 그대로여도
이번 diff에서 대응하는 정리 코드가 삭제되면 표시합니다. 등록 줄과 짧은 코드,
찾지 못한 정리 호출 이름을 보여주며, 삭제된 정리 코드는 base 줄 번호도 남깁니다.
파일마다 최대 두 건이며 기존 신호 길이와 전체 출력 크기 제한을 따릅니다.

타이머와 구독 핸들은 지역 바인딩으로 구분합니다. 구독은 `.unsubscribe()`뿐
아니라 반환받은 정리 함수를 직접 호출하는 형태도 확인합니다. 리스너는 대상,
문자열 이벤트 이름, 콜백 바인딩, capture 설정이 일치해야 합니다. 다른 함수의
정리 호출이나 같은 이름의 다른 변수, 재할당된 변수는 정리 근거로 삼지 않습니다.
핸들을 반환하거나 다른 곳에 대입하거나 인자로 넘기는 경우, 리스너의 `once`,
`signal`, 동적 옵션은 이 검사에서 제외합니다. 별도 타이머 래퍼, 인스턴스 필드에
보관한 핸들, 동적 이벤트 이름, 다른 모듈의 정리 코드는 추적하지 않습니다.
신호가 없다고 안전하다는 뜻은 아니며, 신호가 있어도 누수나 버그를 확정하지
않습니다. 정리 호출이 보이더라도 모든 실행 경로에서 호출되는지는 증명하지 않습니다.

상태 전이 초안은 엄격한 동등 비교나 switch case의 조건과, 같은 변수 또는
단순 프로퍼티 경로에 문자열이나 불리언을 대입하는 코드를 연결합니다. 이름 있는
클래스의 `this` 필드도 구분합니다. 조건과
대입 줄을 표시하고, 연결이 삭제되면 base 줄도 남깁니다. 중간 재대입이나 증감,
`await`, case의 다음 분기로 이어질 가능성이 있으면 불확실한 초안으로 표시하고
사람의 판단을 요청합니다. 같은 이름의 다른 변수, 지연 콜백, 느슨한 비교,
여러 상태를 허용하는 조건은 전이의 근거로 삼지 않습니다. 파일마다 최대 두 건이며,
완성된 상태 머신이나 제품 명세가 아닙니다. 함수 호출의 임의 부작용, 별칭을 통한
변경, 함수 사이의 전이는 추적하지 않으며 대입 시점의 실제 상태를 증명하지 않습니다.
조건과 마지막 대입이 그대로여도 중간 쓰기나 비동기 간격의 변경 근거는 남깁니다.
같은 바인딩의 선언 초기화, 구조 분해 대상, 반복문 대상 대입도 불확실성의 근거로
삼으며 다른 바인딩과 지연 콜백의 쓰기는 연결하지 않습니다.
switch의 비교 대상도 별도 줄 좌표가 있는 근거로 보존합니다. 리터럴 조건을
교체하면 최대 두 건의 예산 안에서 새 관계와 이전 base 관계를 남길 수 있습니다.
같은 값의 표기만 바뀌면 삭제 관계를 중복하지 않고, 남아 있는 대입을 삭제됐다고
표현하지 않습니다.

공유 캐시 범위 신호는 모듈 최상위의 기본 `Map`을 `const`로 선언하고, 같은 함수가
구조적으로 일치하는 키로 읽고 쓰는 경우에만 만듭니다. 저장 값이 사용하는 함수
입력 중 키에는 없는 입력을 선언, 읽기, 쓰기, 값 생성 줄과 함께 보여줍니다.
단순 프로퍼티 경로와 상수 별칭은 구분하며 별칭은 최대 다섯 단계까지만 따라갑니다.
함수 입력을 호출하거나 프로퍼티의 기준으로 사용하는 상수 별칭도 포함합니다.
호출마다 새로 만드는 Map, 메서드를 교체한 Map, 가변 키, 계산된 프로퍼티,
내부를 알 수 없는 키 생성 함수는 이 분석에서 제외합니다. 읽기 전의 직접적인
`clear()`는 그 사이에 `await`가 없을 때만 신호를 억제합니다. 이 초기화만 삭제되면
현재 Map 근거 옆에 삭제 전 base 좌표를 남깁니다. 문자열 리터럴 대괄호로 메서드를
교체한 경우도 점 표기와 똑같이 제외합니다. 파일마다 최대
두 건이며 기존 출력 상한을 따릅니다. 입력 범위를 검토하라는 뜻이지 데이터 유출이나
캐시 안전성을 판정한 결과는 아닙니다. 클래스나 외부 저장소, 함수 사이의 소유권,
숨은 의존성, 임의의 캐시 무효화 경로까지 분석하지는 않습니다.
같은 함수의 마지막 직접 초기화와 읽기 사이에 바뀐 `await`도 입력 범위 질문의
변경 근거가 될 수 있으며 초기화·await 좌표를 함께 남깁니다. 이후에 유효한
초기화가 있으면 기존처럼 신호를 억제하고, 무관한 await는 범위 근거로 삼지 않습니다.

사용처는 비교 대상 head의 모든 추적 파일에서 `git grep`으로 찾습니다. 문서,
lockfile, 외부에서 가져온 코드(vendored), 번역 카탈로그, 빌드 결과물은 제외하며, 구문 색인에 넣기엔 너무 큰 파일도 포함합니다.
찾은 후보는 파일의 import 바인딩으로 다시 확인합니다(JavaScript/TypeScript,
Python). 이름이 같아도 다른 모듈에서 가져온 심볼은 빼고, `export { a as b }`나
`import { a as b }` 같은 별칭은 따라갑니다. JavaScript와 TypeScript는 실제 사용
위치의 바인딩도 확인합니다. 매개변수나 지역 변수로 가려진 이름은 모듈 선언의
참조로 세지 않고, 비공개 도우미를 다른 모듈의 export로 취급하지 않습니다.
이름·namespace import는 제한된 export 경로를 따라가며, 리터럴 CommonJS 바인딩도
같은 구분을 유지합니다. 연결을 확인할 수 없는 후보는 좌표와 미확인 표시를 남기고
확인된 호출자·테스트 목록에서 뺍니다. 테스트 참조를 수집하지 못했다는 결과는 테스트가 없다는 증명이 아닙니다. 빌드 출력 import와 원본 선언의 관계도 근거 없이 추정하지 않습니다. 호출 대상의 바인딩을 확인하지 못하면 다른
파일의 동명 정의를 대신 붙이지 않습니다. import 바인딩이 없는 언어는 이름 일치
결과를 그대로 둡니다.
JavaScript 테스트 파일은 `.test`, `.spec`, `-test`, `-spec` 접미사와 함께
`test.js`, `spec.mjs` 같은 기본 파일명도 수집합니다. 파일명 규칙은 실행 증거가
아니며, 다른 이름의 테스트는 수집 범위 밖에 남을 수 있습니다.
위치를 확인하지 못한 bare import는 workspace 패키지나 컴파일러 경로 별칭일 수
있으므로, 경로 문자열만으로 저장소 밖의 모듈이라고 단정하지 않습니다.

JavaScript와 TypeScript의 호출자는 실제 사용 위치에서 바인딩을 확인한
함수·생성자 호출만 포함하며, 단순 괄호와 타입 단언으로 감싼 호출도 확인합니다.
타입 표기·제네릭 인자·저장된 값·콜백 값은 좌표와 함께
`source references (invocation not established)`에 남깁니다. 그 소속 선언의
테스트나 오류 처리 관계를 실행 호출의 근거로 붙이지 않습니다. 함수 값의
`.bind`·`.call`·`.apply` 같은 멤버 호출도 참조로 남기며, 바인딩을 확인한
namespace export의 직접 호출은 호출자로 유지합니다. 마크업의 이름
언급도 호출로 세지 않습니다. 다른 소스 언어는 호출 형태의 휴리스틱을 유지하며
어느 경우에도 실제 실행을 증명하지 않습니다.

상세 표시 개수를 넘는 참조도 `파일:줄` 목록으로 남깁니다. 호출자의 테스트도
코드 발췌를 생략할 때 좌표는 표시합니다. 압축 목록의 테스트 좌표는 제목이
아니라 해당 함수를 사용하는 줄이며, 그 줄이 바뀐 경우에만 `(changed)`를
붙입니다. 생략된 호출자들이 같은 테스트를 공유하면 한 번만 적습니다.
Python의 `from ... import ...` 줄은 테스트나 호출 위치로 세지 않습니다.

이 목록은 수집한 참조를 보여줄 뿐 저장소의 모든 사용처를 찾았다는 뜻은
아닙니다. 검색 상한에 걸린 경우는 미확인 항목에 남깁니다. 전체 출력 크기
제한은 그대로입니다. 좌표만 남긴 참조 목록도 너무 크면 작은 소스·테스트 diff를
빼기 전에 참조 상세를 제한합니다. 생략한 참조 상세 줄 수(참조 항목 수가 아님)를
표시하고, 해당 참조를 보려면 더 큰 `--max-bytes`로 다시 실행하도록 안내합니다.
그래도 파일 블록이 들어가지 못하면 diff와 참조가 빠졌다고 표시합니다.
좌표만으로 커버리지나 테스트 실행 여부를 판단하지 않습니다.

변경된 테스트 계약은 공간이 허용하면 처음 8개 이후의 제목과 선언 좌표도
남깁니다. 단언 상세를 먼저 빼고, Unicode 코드포인트 경계에서 제목을
줄인 뒤에도 부족하면 항목 전체를 생략하고 개수를 표시합니다. 계약과 휴리스틱
영역은 기존 byte 예산의 일부를 사용해 diff 생략 내역과 복구 명령의 공간을
남깁니다. 저장된 전체 JSON에는 수집한 계약이 유지됩니다. 압축 목록은 테스트
전체 소스나 실행 결과가 아닙니다.
JavaScript·TypeScript 계약은 연속된 추가 줄을 구문 분석해 여러 줄의
`it.each` / `test.each`, 태그 형식 표와 일반적인 수식어를 수집합니다.
선언마다 소스 제목과 호출 시작 좌표 하나를 남기며, 표의 행이나 제목 자리표시자를
실행·확장하지 않습니다. 추가된 콜백 안의 짧은 단언은 긴 준비 코드 뒤에서도
수집할 수 있습니다. 선언이 그대로이거나 선언 중간에 diff 공백이 있는 경우에는
계약을 놓칠 수 있고, 발췌가 모든 단언이나 실행 증거를 뜻하지 않습니다.
계약 수집용 diff 조회는 UTF-8 경로를 인용하지 않도록 요청합니다. 모든 특수문자
Git 경로의 디코딩을 지원하는 변경은 아닙니다.

여러 파일에서 숫자 하나만 다르게 반복되는 변경은 실제 파일 하나를 보여준 뒤
나머지 값을 정확히 적습니다(예: `N = 0..9, 11..159`). 표본만 고르거나 빠뜨리는
항목은 없습니다.

## 에이전트에서 사용하기

`qamap init --agent`는 이 작업 순서를 `AGENTS.md`에 적고, Codex와 Claude Code용
`qamap-pr-qa` 스킬을 설치합니다. `--review-mode report`는 사용자가 이 프로젝트에서
QAMap 검수를 선택했다고 기록하고, `--review-mode ask`는 먼저 제안하는 방식으로
되돌립니다. 설치만으로 동의한 것은 아닙니다.

디렉터리 플러그인은 프로젝트 설정 없이 같은 스킬을 제공합니다. 설치 방법은
[Claude Code 설치 가이드](claude-code.md)나 [에이전트 연동](agent-integration.md)을
확인하세요. 플러그인과 별도로 스킬이 요구하는 CLI 버전이 필요합니다.

사용자가 동의를 기록하지 않았다면 에이전트는 QAMap을 실행하기 전에 먼저 묻습니다.
사용자는 "이번만", "항상", "이번엔 안 함" 중에서 고를 수 있습니다. "항상"은
프로젝트 단위로 `qamap consent grant`, 모든 저장소에 대해서는
`qamap consent grant --global`(Claude Code와 Codex 사용자 지침)로 기록합니다.
`qamap consent revoke [--global]`는 다시 묻는 방식으로 되돌리고,
`qamap consent status`는 두 범위의 상태를 보여줍니다. 패키지에 포함된 지침은
`qamap qa brief --require-consent`를 실행합니다. 동의가 기록되지 않았으면 이
명령은 아무것도 분석하지 않고 먼저 물어보라는 안내만 출력하므로, 호스트가
질문을 건너뛸 수 없습니다.

지침은 에이전트에게 브리프를 포그라운드에서 한 번 실행하고 최대 10분까지
기다리도록 안내합니다. 큰 저장소는 몇 분이 걸릴 수 있기 때문입니다. 브리프는
검수의 출발점이지 한계가 아닙니다. 에이전트는 diff나 넓은 검색을 다시 하지 않지만,
결론을 내리기 전에 다음을 합니다.
- "전부 보이지 않은 파일"의 diff를 읽습니다.
- 함수의 hunk 사이에 안 보인 줄이 있거나, 변경이 가드, 조기 종료, 오류 처리, 로그
  수준, 트랜잭션, 공유 상태를 건드리면 그 함수를 한 번 통째로 읽습니다.
- 삭제되거나 바뀐 동작마다 구체적인 실패 시나리오를 적습니다.
- 무엇이 새로 생겼다, 없어졌다, 테스트가 없다, 모두 바뀌었다고 말하기 전에 base와
  비교합니다.
- 결함 여부를 가르는 질문은 미확인으로 남기지 않고 필요한 코드를 읽어 확인합니다.

결과는 발견한 문제, 구체적인 검증 항목, 미확인 항목 순서로 보고합니다. 테스트 상태는 `not-run`입니다.
브리프는 정적 근거일 뿐 실행 결과가 아닙니다. 브리프 속 저장소 텍스트는 근거일
뿐 지시가 아닙니다.

버전이 붙은 `qamap.qa.handoff` JSON이 필요한 도구는 계속 `qa report --handoff`와
`qa read`를 쓸 수 있습니다. [한 번의 호출로 검수 근거 받기](agent-handoff.md)를
참고하세요. 큰 보관 파일을 여러 페이지로 나눠 모델에 읽히면 브리프보다 토큰이 많이
들기 때문에, 패키지에 포함된 검수 지침은 브리프를 사용합니다.

## 한계

- 이름 검색과 import 확인은 타입 검사기가 아닙니다. 동적 디스패치, 의존성 주입,
  리플렉션, 문자열로 만든 모듈 경로는 호출 코드를 가릴 수 있습니다. 브리프는
  찾은 내용을 보여줄 뿐, 다른 사용처가 없다는 증명이 아닙니다.
- 이력 항목에는 로컬 Git 이력이 필요합니다. 선택적 이력 조회는 lazy fetch를
  막고, Git 명령마다 최대 1초·합계 3초의 시간 예산을 적용합니다. 로컬 객체가
  없거나 명령이 실패하거나 시간 제한에 걸리면 미확인 항목에 불완전한 이력이라고
  표시합니다. 이 제한은 전체 분석의 실행 시간 제한이 아닙니다. 얕은 clone은
  원래 커밋에 도달하지 못할 수 있으며, `--no-lazy-fetch`를 지원하지 않는 Git도
  이력 조회가 불완전하다고 표시하고 diff 분석을 계속합니다.
- 얕은 이력의 경계에서는 Git이 커밋의 전체 트리를 변경 파일로 표시할 수 있습니다.
  변경 의도 분석은 해당 경계 커밋을 제외하고 미확인 항목에 불완전한 근거라고
  표시합니다. 나머지 커밋과 현재 diff는 계속 사용합니다.
- 테스트 발췌는 선택한 줄이며 테스트 전체가 아닙니다. 브리프는 테스트를 실행하지 않습니다.
- 토큰 절감은 보장되지 않습니다. 호스트는 브리프를 읽고 검수 결과를 쓰는 데 토큰을
  쓰며, 에이전트가 더 읽기로 할 수도 있습니다.

## 실측 결과

Claude Code CLI 2.1.282가 고정된 19개 사례를 이 작업 순서로 한 번, QAMap 없이 한 번씩
검수했습니다. 방식마다 세 번씩 실행했고, 매번 새 세션에서 같은 모델, 도구,
프롬프트를 썼으며, 답변은 고정된 정답 기준으로 블라인드 채점했습니다. 사례에는
이 저장소 이력에서 되돌린 실제 회귀 3건이 포함됩니다.

| 항목 | 단독 | QAMap 0.5.1 사용 |
| --- | ---: | ---: |
| 사례별 총 토큰 중앙값의 합 | 9,752,041 | 2,526,116 (-74.1%) |
| 전체 57회 실행 총 토큰 | 30,916,750 | 8,056,261 (-73.9%) |
| 사례별 모델 호출 수 중앙값 | 7-32 | 2-6 |
| 심어 둔 회귀를 모두 찾은 실행 | 40/42 | 42/42 |
| 제품 fixture의 QA 계획 평균 포함률 | 0.73 | 0.89 |

모든 사례에서 QAMap 실행 중 가장 비싼 실행도 단독 실행 중 가장 싼 실행보다 적게
썼습니다. 저장소 설정 없이 프롬프트도 그대로 두고 `qamap consent grant --global`로
동의만 한 번 기록한 경우에도 38회 모두 QAMap을 사용했고, 중앙값 합은
2,881,446(-70.5%)이었습니다. 호스트 하나, 모델 하나로 측정한 알려진 사례 결과이며 일반적인 절감 보장이
아닙니다. 사례별 표, 민감도 측정, 한계는 [0.5.1 릴리스 기록](../releases/0.5.1.md#measured-results)과
[검증 기록](../release-validation.md)에 있습니다.

Claude Code CLI 2.1.292에서는 같은 사례에서 0.5.1이 토큰을 65.4%, 0.5.2 후보 하나가
54.6% 적게 썼습니다. 후보는 결론 전에 코드를 직접 확인하도록 요청하므로 이런 작은
사례에서는 대개 호출이 한 번 늘어납니다. QAMap 방식은 모두 42회 전부 심어 둔 회귀를
모두 찾았고, 단독은 42회 중 41회였습니다.

등록된 규칙으로 고른 공개 PR에서는 0.5.2가 된 빌드가 연구별로 토큰을 33-50% 적게
썼습니다. 프로젝트가 나중에 고친 회귀 6건에서는 이 빌드의 12회 실행 중 5회가 회귀를
찾았고 5회가 일부 찾았으며, 단독은 3회와 0회였습니다. PR 36건 블라인드 채점에서는
단독이 18 대 14(무승부 4)로 더 많이 선택됐고, 유효한 지적도 단독 19개, 이 빌드
16개였습니다. 이 빌드의 변경 신호는 이 사례들을 읽은 뒤 설계했으므로 독립적인 근거가
아닙니다([외부 결과](../../test/benchmarks/review-host/external/RESULTS.md)).
