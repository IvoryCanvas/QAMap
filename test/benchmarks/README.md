# Public benchmark fixtures

Each directory represents one reduced pull request:

- `base/` is committed on a temporary `main` branch.
- `head/` is copied over the baseline and committed on `benchmark/change`; intent fixtures provide a neutral synthetic `commitMessage`.
- A target may instead declare `commits: [{dir, message}]` overlays that are committed sequentially, materializing a multi-commit branch such as a feature commit followed by a cleanup tip commit.
- `bench.config.json` declares the human expectation for the resulting QA draft.

Fixtures must stay small, synthetic, and safe to publish. The benchmark runner only reads the materialized repositories. It does not install dependencies, start services, run package scripts, or execute generated tests.

Fixture manifests exist only to exercise static framework and runner detection. They are excluded from Dependabot updates because their packages are never installed; changing a fixture version does not remediate a runtime dependency in QAMap.

The committed matrix includes React/Next.js, Vue, SvelteKit, Expo/React Native, API, CLI, artifact, shared-component, configuration-only, release-only, and test-only changes. Dedicated web preferences and mobile reminder fixtures protect commit intent, lifecycle ordering, failure and boundary QA, generic-title suppression, and commit-backed Behavior Graph evidence. The release-gate fixture requires synchronized package, plugin, changelog, benchmark, and source-version metadata to select one non-publishing repository gate without repeating its nested test or provider-free benchmark commands. The long-PR fixture keeps four unrelated behavior groups separate despite broad package vocabulary, joins two commits that change the same compatibility lifecycle, and leaves release notes as supporting provenance. The runtime-provider fixture requires a new route to retain its import chain, fail-fast context contract, and app-wrapper bypass as one critical render scenario while rejecting a component-mocked test as sufficient proof. The symbol-annotated renewal fixture requires optional JSDoc context to refine a genuinely changed export while parser tests reject annotation-only and neighboring-symbol changes. The multi-surface React fixture requires each affected flow to retain and compile its own action and assertion instead of passing on aggregate counts from one stronger flow. The CLI analysis-rule fixture is a negative control: analyzer vocabulary such as scheduling, routing, `/api`, fixture, and mock must remain rule-test evidence instead of becoming product QA. The analyzer contract cluster fixture requires one rule, its changed import/export adapters, matching result schema, and focused regression test to remain one repository-verification flow. The untrusted repository text fixture keeps real profile-update evidence while requiring instruction-like UI text to be neutralized and barred from escalating the selected action. Framework fixtures also protect route discovery, changed selectors, success signals, and draft paths rather than framework branding alone.

Add a fixture when a real failure can be reduced to a reusable project shape. Prefer one clear regression per fixture over a large imitation of a production repository.
