# Public benchmark fixtures

Each directory represents one reduced pull request:

- `base/` is committed on a temporary `main` branch.
- `head/` is copied over the baseline and committed on `benchmark/change`; intent fixtures provide a neutral synthetic `commitMessage`.
- A target may instead declare `commits: [{dir, message}]` overlays that are committed sequentially, materializing a multi-commit branch such as a feature commit followed by a cleanup tip commit.
- A target may declare `workingTreeDir` to copy one final overlay without committing it and run the same analysis with working-tree inclusion enabled.
- `bench.config.json` declares the human expectation for the resulting QA draft.

Fixtures must stay small, synthetic, and safe to publish. The benchmark runner only reads the materialized repositories. It does not install dependencies, start services, run package scripts, or execute generated tests.

Fixture manifests exist only to exercise static framework and runner detection. Commit dependency manifests with a `.fixture` suffix, such as `package.json.fixture` or `requirements.txt.fixture`. The benchmark runner restores the canonical filename only inside its isolated temporary repository. This keeps fixture packages out of repository dependency alerts without changing the repository shape that QAMap analyzes. Fixture packages are never installed, so changing a fixture version does not remediate a runtime dependency in QAMap.

The committed matrix includes React/Next.js, Vue, SvelteKit, Flutter, Expo/React Native, API, CLI, artifact, shared-component, configuration-only, release-only, test-only, and working-tree changes. The working-tree test-contract fixture requires a changed product file and its same-owner test to recover one review-required intent, preserve the exact test title, select the focused test command, and ignore an unchanged neighboring surface with similar vocabulary. The Flutter profile fixture requires structured `pubspec.yaml` evidence to win over generic native-directory signals, retains the changed Dart test contract, and routes the focused `flutter test` command before the full suite. Dedicated web preferences and mobile reminder fixtures protect commit intent, lifecycle ordering, failure and boundary QA, generic-title suppression, and commit-backed Behavior Graph evidence. The release-gate fixture requires synchronized package, plugin, changelog, benchmark, and source-version metadata to select one non-publishing repository gate without repeating its nested test or provider-free benchmark commands. The long-PR fixture keeps four unrelated behavior groups separate despite broad package vocabulary, joins two commits that change the same compatibility lifecycle, and leaves release notes as supporting provenance. The runtime-provider fixture requires a new route to retain its import chain, fail-fast context contract, and app-wrapper bypass as one critical render scenario while rejecting a component-mocked test as sufficient proof. The symbol-annotated renewal fixture requires optional JSDoc context to refine a genuinely changed export while parser tests reject annotation-only and neighboring-symbol changes. The multi-surface React fixture requires each affected flow to retain and compile its own action and assertion instead of passing on aggregate counts from one stronger flow. The CLI analysis-rule fixture is a negative control: analyzer vocabulary such as scheduling, routing, `/api`, fixture, and mock must remain rule-test evidence instead of becoming product QA. The analyzer contract cluster fixture requires one rule, its changed import/export adapters, matching result schema, and focused regression test to remain one repository-verification flow. The untrusted repository text fixture keeps real profile-update evidence while requiring instruction-like UI text to be neutralized and barred from escalating the selected action. Framework fixtures also protect route discovery, changed selectors, success signals, and draft paths rather than framework branding alone.

Add a fixture when a real failure can be reduced to a reusable project shape. Prefer one clear regression per fixture over a large imitation of a production repository.
